# Границы безопасности

## Текущая версия 0.2

Приложение — статический web-клиент. Партия и настройки хранятся в браузере. Серверной базы, SQL-запросов, аккаунтов и публичного API пока нет. Отсутствие SQL в этой версии не является гарантией безопасности будущего сервера.

### Входные данные

- ChessGame принимает ходы только через chess.js; нелегальные ходы не изменяют позицию.
- Записи FEN ограничены 256 символами, проверяются структура, короли, рокировочные права и поле en passant.
- Внутренняя запись PGN ограничена 200 КБ; пользовательского импорта/экспорта на игровом экране нет.
- Сохранение ограничено 1 МБ. Восстановление проверяет версию, тип соперника, движок, сторону, допустимые часы и числовые остатки времени. Ошибка сохранения не должна ломать запуск приложения.
- Текст отображается средствами React; HTML из PGN не исполняется. Нет dangerouslySetInnerHTML или пользовательского JavaScript.

### Движок

- Stockfish работает в отдельном Worker, а не в потоке интерфейса.
- Файлы движка поставляются с приложением. Произвольные URL движков не принимаются.
- Позиции формируются из проверенной модели. Переводы строки в UCI-команде отклоняются.
- Каждый ответ проверяется на соответствие текущей партии и позиции, а полученный ход снова проходит проверку правил.
- Отмена и новая партия инвалидируют старые запросы. Есть предел ожидания загрузки/ответа и возможность повторного запуска.

### Web-окружение

`config/security.mjs` задаёт CSP, nosniff, Referrer-Policy, запрет встраивания и отключение неиспользуемых разрешений. Production CSP не разрешает inline-скрипты или обычный unsafe-eval; wasm-unsafe-eval нужен для компиляции WebAssembly. Inline-стили нужны для координат перетаскивания. В dev отдельно разрешены React Refresh и локальный WebSocket.

Vite preview применяет production-заголовки. Сборка создаёт файл `_headers` для хостингов с таким форматом. На другом web-сервере/edge эти же правила нужно настроить отдельно; одного файла в каталоге недостаточно. Публичный релиз — только по HTTPS, с HSTS на уровне выбранного хостинга.

## До появления аккаунтов и общей базы

Обязательные условия будущей реализации:

1. Проверять схему, тип, диапазон и размер каждого запроса на сервере. TypeScript и проверка в браузере не заменяют серверную проверку.
2. Использовать параметризованные SQL-запросы и минимальные права пользователя БД. Не собирать запросы конкатенацией пользовательского текста.
3. Проверять доступ к каждой партии/коллекции по владельцу на сервере, а не по данным из клиента.
4. Безопасные сессии, HttpOnly/Secure/SameSite cookies, защита изменяющих запросов от CSRF, ограничение частоты и размера запросов.
5. Хранить секреты на сервере, не в JavaScript, приложении или localStorage. Не писать токены/персональные данные в логи.
6. Для рейтинговой сетевой игры сервер должен владеть часами, правилами и результатом. Текущая локальная модель предназначена для практики и не защищает рейтинг от изменения клиентом.
7. Миграции, резервные копии, восстановление, удаление данных, тесты авторизации и проверка зависимостей перед релизом.

## Проверки

Автоматически проверяются запрет инъекции UCI-команд, ограничение ввода, повреждённые сохранения, текстовые PGN-заголовки и production CSP. `pnpm audit --prod` на момент проверки не обнаружил известных уязвимостей. Это проверка базы advisory, а не полный аудит безопасности или гарантия отсутствия ошибок.
