# Архитектура

## Решение ADR-001: локальное приложение с web-интерфейсом

Прототип — React + TypeScript + Vite. Это позволяет проверить дизайн в браузере и сохранить UI при переходе к Windows-оболочке. Desktop bridge и установщик выбираются перед интеграцией native Stockfish; кандидат — Tauri. Упаковка не входит в этапы 1–2.

## Границы

```
React views → application state → domain ports
                                  ├─ ChessRules (этап 3)
                                  ├─ EngineService (этап 5)
                                  ├─ GameRepository (этап 7)
                                  └─ CurriculumRepository (этап 9)
```

В прототипе сценарные данные хранятся в `src/data`. Настройки и закладки — versioned localStorage. Это не финальное хранилище партий; целевое локальное хранилище — SQLite в desktop-приложении. Учебный контент — валидируемые JSON/Markdown-файлы с версией схемы.

## ADR-002: достоверность

Демонстрационная партия воспроизводится из зафиксированных позиций. UI явно сообщает, что движок не подключён. Не показывать имитацию живых часов, глубины анализа или рейтинг пользователя. Будущий EngineService возвращает requestId, FEN, глубину, время, score, PV; ответы устаревших запросов отбрасываются. Объяснения обязаны ссылаться на ту же позицию.

## ADR-003: графика

Фигуры — оригинальные SVG из набора Cburnett в Lichess, без изменения содержимого. Все 12 изображений поставляются локально; ссылка на исходную ревизию и хеши находятся в public/pieces/SOURCE.json. Никаких 3D-моделей, генератора фигур или зависимости Three.js. Доска — плоская сетка однотонных полей. Лицензии и атрибуция сохранены в docs/ASSETS.md.

## ADR-004: отсутствие обязательных сетевых сервисов

Прототип работает без API, аккаунта и платной модели. Шрифты поставляются локально. Будущая синхронизация и свободные объяснения опциональны. Доступ к сети не требуется для основных локальных сценариев.

## Критерии расширения

- Логика шахмат не должна находиться в React-компонентах.
- Не добавлять full backend до необходимости синхронизации.
- Функциональные изменения проверять на поведении пользователя, не на деталях реализации.
- Сохранить миграции данных, экспорт и границы лицензирования до первого публичного релиза.
